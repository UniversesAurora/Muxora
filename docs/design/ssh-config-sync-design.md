# SSH config 修改与同步设计

状态：设计稿，2026-10-19。修订 [V0 设计 §5](v0-design.md#5-会话管理与-ssh-config) 的只读规则：默认仍然只读，用户可以在设置中打开两个独立选项。实现步骤见 [阶段 7.4h–7.4m](../roadmap/implementation/phase-7-terminal-and-sessions.md#74-会话目录与-ssh-config)。

## 1. 两个选项

| 设置 | 默认 | 打开后的行为 |
| --- | --- | --- |
| `ssh.config.allowEditing`（允许修改 SSH config 中的连接） | 关闭 | SSH config 来源的会话可以在 Muxora 中编辑连接参数（地址、用户、端口、密钥、跳板、代理、转发等），修改**写回定义该别名的那个 config 文件**；也可以在 Muxora 中新建、重命名、删除 config 中的主机。 |
| `ssh.config.syncAppSessions`（与 SSH config 同步应用会话） | 关闭 | Muxora 自建的会话实时同步到一个由 Muxora 管理的 config 文件中（新增、修改、删除、重命名都同步），并通过 `~/.ssh/config` 中的一行 `Include` 让 `ssh`、`scp`、VS Code Remote-SSH 等外部工具直接使用；外部对该文件的修改也同步回 Muxora。 |

两个都关闭，就是原来的只读设计（V0 设计 §5.2）。两个选项互相独立，可以只开一个：

| 组合 | 用户自己的 config | Muxora 管理的 config | 应用会话 |
| --- | --- | --- | --- |
| 都关闭 | 只读 | 不存在 | 只在 Muxora 中 |
| 只开“允许修改” | 可以编辑 | 不存在 | 只在 Muxora 中 |
| 只开“同步” | 只读（只追加一行 `Include`，见 §4.2） | Muxora 读写 | 与管理文件双向同步 |
| 都打开 | 可以编辑 | Muxora 读写 | 与管理文件双向同步 |

相关的辅助设置：

| 设置 | 默认 | 说明 |
| --- | --- | --- |
| `ssh.config.confirmWrites` | `true` | 每次写入用户自己的 config 文件前显示差异预览并确认；Muxora 管理的文件不需要确认 |
| `ssh.config.managedFile` | `~/.ssh/muxora/config` | 同步使用的管理文件位置 |
| `ssh.config.protectedFiles` | `[]` | 永远不写入的文件（通配），例如由 Ansible、OrbStack、Colima 等工具生成的 `Include` 文件 |
| `ssh.config.backupCount` | `10` | 每个被写入的文件保留的备份数量 |

## 2. 不破坏无关配置：无损解析与最小修改

任何写入都遵守以下规则：

1. **无损解析**：解析器生成保留全部原文的语法树：每一行的缩进、注释（整行和行尾注释）、空行、关键字大小写、关键字与值之间用空格还是 `=`、引号、续行、未知或 Muxora 不认识的指令、`Match` 块、换行符（LF／CRLF）、文件开头的 BOM、文件末尾是否有换行。**不修改任何东西时，重新输出的文本与原文逐字节相同**（测试用大量真实样例保证）。
2. **语义化的修改请求**：界面产生的修改不是“新的文件内容”，而是一组操作：“在别名 `dev` 的块中把 `Port` 设为 `2222`”“删除块 `old`”“在文件末尾追加块 `new`”。写入时把操作应用到**当前**文件内容上，只替换受影响的行或插入新行。
3. **新增行的格式跟随周围**：缩进、关键字大小写和分隔符（空格或 `=`）取同一块中已有指令的写法；块中没有指令时取同一文件中最常见的写法；默认四个空格缩进、`Keyword value`。
4. **不改顺序、不整理、不格式化**：不重排指令，不去掉重复项，不规范化大小写，不删除 Muxora 不认识的指令和注释。
5. **只写一个文件**：修改只写定义该块的那个文件（根配置或某个 `Include` 文件）；`protectedFiles` 中的文件一律不写，相关会话在界面中显示为只读并说明原因。

## 3. 修改用户自己的 config（`allowEditing`）

### 3.1 改到哪里：遵守 ssh 的“第一个值生效”规则

OpenSSH 对每个参数采用**第一次得到的值**：按文件顺序，所有匹配该主机的 `Host`／`Match` 块中，最先设置该参数的块决定它的值。因此“修改某个别名的端口”不能简单地找到它的块写进去：

| 情况 | 处理 |
| --- | --- |
| 别名有自己的块，该块已经设置这个参数 | 原地替换这一行的值 |
| 别名自己的块没有设置这个参数，且它位于所有同样匹配该主机并设置了这个参数的块之前（例如 `Host *` 在后面） | 在别名自己的块中新增一行 |
| 当前生效的值来自排在前面的通配块（例如文件开头的 `Host *` 设置了 `User`） | 不修改通配块（会影响所有主机）。提示用户：要让设置生效，需要把这个别名的块移到该通配块之前；预览移动后的差异，用户确认才执行；也可以取消 |
| 别名出现在多个块中 | 修改第一个定义该参数的块；没有块定义时修改第一个匹配块 |
| 中间存在 `Match` 块 | Muxora 不执行 `Match exec`，无法静态判断它是否匹配。写入前提示“存在条件规则，修改可能不生效”，并在预览中标出这些 `Match` 块 |

“当前生效值”只做静态分析（`Host` 模式匹配加文件顺序），不运行 `ssh -G`。用户可以在详情页手动执行一次“用 ssh 检查有效配置”（即 `ssh -G <别名>`，属于用户发起的诊断，与 V0 设计一致）。

### 3.2 一个块对应多个别名

`Host dev build` 这样的块同时属于两个别名。修改 `dev` 的参数会同时影响 `build`。处理方式：

- 默认提示“这个块同时被 build 使用”，提供两个选择：**同时修改**（改块本身），或者**拆出 dev**：从模式列表中去掉 `dev`，在原块之前插入一个只含 `dev` 的新块（复制原块的全部指令，再应用这次修改）。拆分保证 `dev` 原有参数不变，`build` 完全不受影响。
- 预览中显示完整差异，用户确认后执行。

### 3.3 新建、重命名、删除

- **新建主机**：追加到根配置末尾、所有 `Host *` 通配块之前（否则通配块中的值会优先）；或者用户选择的 `Include` 文件。别名必须是合法的主机模式（不含空格、`*`、`?`、`!`、`,`），且不能与现有别名重复。
- **重命名**：只替换模式列表中的这一项。被重命名的别名如果出现在其他块的模式中（例如 `Host dev staging` 与后面的 `Host dev`），提示并列出所有出现位置，用户选择全部替换或只改这一个块。
- **删除**：只有一个模式的块整块删除（包括紧挨着块头、明显属于它的注释，即块头上方连续的注释行，直到空行为止）；多模式块只从列表中去掉这个别名。删除前预览并确认。
- 应用设置（显示名、分组、字体等）仍保存在 Muxora 的 `ssh-alias-overrides.json`，不写进 config。

### 3.4 可编辑的参数

图形界面编辑常用参数：`HostName`、`User`、`Port`、`IdentityFile`（可多个）、`IdentitiesOnly`、`ProxyJump`、`ProxyCommand`、`ForwardAgent`、`ForwardX11`、`ForwardX11Trusted`、`LocalForward`、`RemoteForward`、`DynamicForward`、`ServerAliveInterval`、`ServerAliveCountMax`、`ConnectTimeout`、`Compression`、`StrictHostKeyChecking`、`UserKnownHostsFile`、`RequestTTY`、`RemoteCommand`、`SetEnv`。

其他指令在“高级”区域以只读列表显示，并提供“在编辑器中打开 config 并定位到此块”（阶段 5 的内置编辑器，后续加入 ssh_config 高亮）。Muxora 不提供编辑 `Match` 块和 `Include` 指令本身的图形界面。

**秘密永不写入**：密码、私钥口令、MFA 结果只进入系统凭据库；config 中只出现密钥文件路径。

## 4. 同步应用会话（`syncAppSessions`）

### 4.1 管理文件

应用会话写入一个独立文件（默认 `~/.ssh/muxora/config`），而不是直接写进用户的 `~/.ssh/config`：

```text
# This file is managed by Muxora. Changes made here are synced back to Muxora.
# Muxora keeps comments that it does not own. See ssh.config.syncAppSessions.

# muxora-session: 7f3c2a90-...
Host prod-db
    HostName 10.0.0.12
    User admin
    Port 2222
    IdentityFile ~/.ssh/id_ed25519
```

- 每个块上方有一行标记注释 `# muxora-session: <会话 ID>`，用来在外部改名、调整顺序后仍能对应到同一个 Muxora 会话。
- 写入的只有 ssh 能理解的连接参数（§3.4 中的集合）；Muxora 特有的内容（分组、显示名、登录脚本、字体、终端设置、凭据引用）只保存在 Muxora 的会话文件中。
- 别名由会话名生成（去掉空格和非法字符、转为小写、冲突时加后缀），可以在会话设置中修改；会话显示名与别名分开。

### 4.2 接入 `~/.ssh/config`

打开同步时，需要让 ssh 读到管理文件：

1. 检查 `~/.ssh/config` 是否已经包含指向管理文件的 `Include`。
2. 没有时，准备在文件**最开头**（第一个 `Host`／`Match` 之前，保留已有的开头注释）插入：

   ```text
   # Added by Muxora for synced sessions (ssh.config.syncAppSessions).
   Include muxora/config
   ```

   必须放在开头：`Include` 写在某个 `Host` 块之后，会变成只在该块匹配时才读取。
3. 显示差异预览，用户确认后写入；文件不存在时创建一个只含这两行的文件。
4. 这是同步功能对用户 config 的唯一修改，即使 `allowEditing` 关闭也需要这一步，所以单独确认。用户拒绝时，同步仍然维护管理文件，并提示“外部工具需要手动 Include 该文件”。

**放在开头的影响**：管理文件中的主机排在用户所有块之前，会优先生效。如果用户自己的 config 中已经有同名别名，会发生覆盖。因此打开同步时先检查冲突（§4.4）。

### 4.3 双向同步

- **Muxora → 文件**：会话新增、修改、删除、重命名后，合并到下一个事件循环批量写入管理文件（同一轮多次修改只写一次）。
- **文件 → Muxora**：监听管理文件（父目录监听与去抖动，与 SSH config 来源相同）。外部的修改按标记注释对应到会话并更新其连接参数；新增的无标记块作为新会话导入并补上标记；删除的块对应的会话被删除（进入“最近删除”，可在 30 天内恢复，见 §6）。
- **冲突**（2026-10-19 修订：由用户选择，不自动决定）：Muxora 保存每个会话最近一次同步时的参数快照，按参数逐项三方合并：
  - 只有一边改的项：直接采用，不打扰用户。
  - 两边改成不同值的项，以及“一边删除了会话、另一边修改了它”的情况：**弹出冲突对话框让用户选择**。对话框逐项列出“参数名、上次同步的值、文件中的值、Muxora 中的值”，每项可选“用文件中的值”或“用 Muxora 中的值”；底部有“全部用文件”“全部用 Muxora”。删除与修改冲突时，选项为“保留会话（用 Muxora 的修改重新写回文件）”或“删除会话”。
  - **必须马上处理**（2026-10-19 用户要求）：冲突对话框没有“稍后处理”，也没有取消；`Esc` 和关闭按钮不可用，只有每一项都选定后“确认”才可用。对话框**对整个应用模态**（`Qt::ApplicationModal`）：会话在所有窗口之间共享，只挡住一个窗口的话，用户切到别的窗口就能绕过它。显示期间所有完整窗口和浮窗都不接受鼠标与键盘操作。
  - 模态只阻止用户操作，不暂停后台工作：所有终端照常收发数据、刷新显示，传输任务继续进行。
  - 用 `open()` 异步显示，不启动嵌套事件循环（界面规范 §1 第 4 条）。
  - 显示位置：当前活动的 Muxora 窗口；Muxora 不在前台时（例如用户在别的程序里改了 config），不抢焦点，只让任务栏按钮闪烁，用户切回 Muxora 时对话框已在最前。点击任何被挡住的 Muxora 窗口，对话框闪烁并回到最前。
  - 对话框显示期间：管理文件中这个块不被 Muxora 改写（外部工具看到的仍是文件中的值）；该会话暂停同步；其他会话的外部修改先读入并等待，对话框关闭后再统一应用（避免在用户无法操作时改动界面）。已经打开的连接不受影响。
  - 对话框期间又出现新的冲突：加入同一对话框，按会话分页；全部会话都确认后才关闭。
  - 冲突状态写入会话文件。程序在处理完之前崩溃或被强制结束时，下次启动在主窗口显示后立即重新弹出对话框。
  - 冲突未处理完时退出程序：先显示冲突对话框，处理完才继续退出。
- 用户手写在管理文件中、不属于任何会话的注释和指令（例如文件开头的 `Host *` 块）保留不动。

### 4.4 打开同步时的处理

1. 选择管理文件位置（默认值即可），确认 §4.2 的 `Include`。
2. 计算全部应用会话的别名，检查与用户 config 中别名的冲突。列出冲突项，每项可选“改用另一个别名”（默认加后缀）、“不同步此会话”、“以 Muxora 为准”（会遮住用户的同名主机，需要再次确认）。
3. 写入管理文件；之后进入实时同步。
4. 全过程显示在一个多步快速输入或对话框中，可以在确认前取消，取消时不写任何文件。

### 4.5 关闭同步时的处理

用户在设置中关闭这个开关时，**立即弹出选择对话框**，三个按钮，不预先替用户做选择：

| 选项 | 结果 |
| --- | --- |
| 保留文件 | 管理文件和 `Include` 保持不变，外部工具仍能用这些主机，但之后不再更新；文件开头的说明注释改为“已停止同步” |
| 移除文件 | 删除 `~/.ssh/config` 中 Muxora 加入的 `Include` 两行（只删除带 Muxora 说明注释的那两行），并删除管理文件；两者都先备份，并显示将要删除的内容 |
| 取消 | 开关恢复为打开，继续同步 |

- `Esc` 或关闭对话框等于“取消”。
- 对话框完成前，开关在界面中显示为“正在关闭”，同步暂停但不写文件；选择“保留文件”或“移除文件”并完成写入后，开关才真正变为关闭并保存到 `settings.json`。
- 用户直接编辑 `settings.json` 把开关改为 `false` 时，Muxora 在检测到变化后弹出同样的对话框；选择“取消”会把 `settings.json` 中的值改回 `true`（用阶段 3.6 的 JSONC 局部修改，保留注释）。
- 冲突对话框正在显示时，不能关闭这个开关（设置页中该开关暂时禁用并提示“请先处理同步冲突”）。

应用会话本身不受影响。

## 5. 安全写入

1. **基于当前内容**：写入前重新读取文件；修改操作应用到读到的最新内容上。如果读到的内容与界面打开编辑时不同，而且外部修改涉及同一个块的同一个参数，停止写入并提示冲突（显示外部的新值）；不同块或不同参数的外部修改正常保留。
2. **原子替换并保留文件属性**：先写同目录下的临时文件，再用 `ReplaceFileW` 替换。`ReplaceFileW` 保留原文件的访问控制列表、属性和创建时间——Windows 版 OpenSSH 会检查 config 的权限，如果替换后权限变成继承的默认值，ssh 可能拒绝读取。不使用直接“写新文件再重命名”的方式。
3. **符号链接**：config 是符号链接（例如 dotfiles 仓库）时，写入链接指向的目标文件，不把链接替换成普通文件。
4. **编码与换行**：保持原文件的换行符、BOM 和末尾换行。
5. **写后校验**：写入后重新解析，确认语法树中目标修改存在、其余部分与写入前逐字节一致；不一致时用备份恢复并报告。
6. **备份**：每次写入用户自己的文件前，把原内容保存到 Muxora 状态目录下的 `ssh-config-backups/<文件名>-<时间>.bak`，每个文件最多保留 `backupCount` 份。命令“撤销上次 SSH config 修改”恢复最近一份备份（同样经过预览和确认）。
7. **预览**：`confirmWrites` 打开时，写入用户文件前显示统一差异视图（只显示改动的行及上下各 3 行），确认后写入。

## 6. 删除与恢复

- 删除应用会话（同步开启时会同时删除管理文件中的块）后，会话进入“最近删除”，30 天内可以恢复；恢复时重新写入管理文件。
- 删除用户 config 中的主机（`allowEditing`）依靠 §5 的备份撤销，不进入“最近删除”。
- V0 设计 §5.4 中“别名从来源中消失后不保留旧入口”的规则仍然适用于用户自己的 config：外部删除了别名，Muxora 不复活它。

## 7. 与只读模式的关系

- 两个选项都关闭时，V0 设计 §5 的全部规则不变，包括“任何操作都不改变 config 文件”的自动化检查。
- 打开 `allowEditing` 后，只读规则改为“只在用户明确发起的修改中写入，并遵守本文 §2、§3、§5”。
- 后台刷新、索引、连接都不写文件；写入只来自用户在界面或 Lua 中发起的修改，以及同步功能对管理文件的写入。
- Lua：`muxora.ssh.config` 提供读取与修改接口，修改同样经过 §2、§5 的规则，并受两个开关约束（开关关闭时返回错误）。
