# 0008 本地脚本使用完整 Lua 标准库，与 Neovim 一致

**状态**：采用（取代 [0003](0003-lua-sandbox-scope.md)；实现见 [阶段 9.8](../roadmap/implementation/phase-9-lua-extension-api.md#98-本地脚本使用完整标准库与-neovim-一致)，完成前代码仍是 0003 描述的范围）

## 背景

0003 把脚本限制在纯计算的标准库里，文件、命令、网络等能力计划逐项做成 `muxora.*` 接口，并考虑按能力做权限管理。复核后发现这条路有两个问题：

- **重造轮子**：文件读写、执行命令、加载模块，Lua 标准库已经有了。另做一套 `muxora.files` 之类的接口，只是把标准库换个名字，现成的 Lua 库也用不了。
- **权限管理没有对象**：脚本就是用户自己放在 `User/` 下的 Lua 文件，没有安装别人扩展包的机制。按能力逐项询问只会打扰写脚本的人本身。

同类软件的做法：Neovim 的 Lua、WezTerm 的 Lua 配置都直接提供完整的 `io`、`os`，不做权限管理。

0003 中还有一处与代码不符：受限的 `require` 当时已经实现（经宿主读取模块目录中的文件，限制路径、严格 UTF-8、1 MiB 上限、检测循环加载），0003 写成了“尚未实现”。

## 决定

用户 2026-10-20 决定：

- 本地脚本可以使用全部 Lua 标准库：`io`、`os`（含 `os.execute`、`io.popen`）、`debug`、`package`／`require`、`coroutine`、`load`（含二进制块）、`string.dump`、`collectgarbage`。
- 文件、命令、模块直接用标准库，`muxora.*` 只提供标准库没有的能力：界面、窗口与标签、会话与终端、SFTP、剪贴板、网络请求、文件监听等。
- 不做权限管理。以后支持安装别人发布的扩展包时，再单独设计。
- 运行时的预算只用来防止脚本失控（死循环、内存失控），不限制正常用途。

为了让开放后的功能正常工作，运行时在内部做以下处理，这些处理不限制脚本：

- 协程转发宿主调用的让出，使 `muxora.*` 在用户自己的协程里照常可用；
- `debug.sethook` 与预算钩子共存，用户钩子照常触发，预算仍然有效；
- `os.exit` 走应用正常的退出流程，先保存再关闭；
- 程序以 UTF-8 作为进程代码页，标准库可以处理含中文的路径；
- 执行时间按 Lua 线程的 CPU 时间计算，阻塞在文件读写或等待外部程序时不计入。

## 后果

- 从网上复制来的脚本拥有与用户相同的权限，靠“只运行自己放进去的脚本”保证安全，与 Neovim 相同。
- 标准库的阻塞调用（读大文件、等待 `os.execute`）期间，其他 Lua 脚本要等待；Lua 在独立线程运行，界面不受影响。不阻塞的写法需要的场合，由 `muxora.*` 的异步接口提供（例如 9.5 的 `app.run`）。
- **不支持 C 模块（DLL）**：Lua 按 C++ 编译并静态链接在程序中（[0002](0002-lua-as-cxx-with-gc-hook.md)），没有 Lua DLL 供外部模块链接，按 C 编译的模块也不能和它混用。纯 Lua 模块可以直接 `require`。
- 原来 `require` 的路径限制、严格 UTF-8 检查和 1 MiB 上限取消，相关测试断言按本决定删除。
- `debug` 开放后，脚本可以读写任意局部变量和上值，包括运行时私有的包装函数；这只影响脚本自己，运行时的停止保证由 C 实现的钩子和粘滞的中止状态维持，不依赖这些包装不被看到。
- 预算默认值（每次运行 10 秒 CPU 时间、512 MiB 内存）和设置项在实现前再与用户确认。
- 以后引入扩展包时，需要另起 ADR 决定扩展包是否受限、怎样声明权限。

## 替代方案

- **维持 0003 的范围，逐项提供 `muxora.*` 接口并做权限管理**：重造标准库的功能，现成 Lua 库不能用，权限询问对本地脚本没有意义。
- **开放标准库但保留 `debug`、二进制 `load` 等少数限制**：用户希望与 Neovim 一样全部开放；这些限制原本保护的“脚本一定能停下来”改由运行时内部的钩子共存和协程转发保证。
