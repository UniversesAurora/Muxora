# 文档维护规范

Muxora 由几个助手轮流开发，彼此只通过仓库交接，所以文档必须做到：每类信息只有一个权威位置，从入口能找到，每次提交后都反映最新状态。本文规定这三点怎么落实，做法参照当前多助手协作项目的通行实践：根规则文件（AGENTS.md）只放共用规则和链接，细节按需链接；每类信息一个权威位置；进度和交接状态集中在交接记录；能自动检查的用脚本检查。协作流程见 [AGENTS.md](../../AGENTS.md)，提交方式见 [参与开发](../../CONTRIBUTING.md)。

## 每类信息只放一处

下表是各类信息的权威位置。其他地方需要提到时，写一句话并链接过去，不复制内容、数值或规则清单。两处说法冲突时以表中位置为准，并在同一个提交里修正另一处。

| 信息 | 权威位置 | 不放在 |
| --- | --- | --- |
| 助手必须遵守的规则、常用命令 | [AGENTS.md](../../AGENTS.md)（只写规则本身，细节链接到下面各文档） | 个人全局配置；细则 |
| 提交拆分、提交信息格式、整合方式 | [CONTRIBUTING.md](../../CONTRIBUTING.md) | AGENTS.md 只写一句并链接 |
| 产品行为与界面要求（最终目标） | `docs/design/`；窗口交互的具体规则在 [窗口交互细则](../design/window-interaction-design.md)，概要文档只写结构 | 实现计划、预览说明 |
| 有长期影响的决定及理由 | [ADR](../adr/README.md) | 设计文档只写结论并链接 |
| 工程、代码、资源规范 | [工程设计](engineering-design.md) | AGENTS.md |
| 测试规则、测试入口用法 | [测试要求](testing-design.md) | AGENTS.md 只写必须用的命令 |
| 文档本身的规则 | 本文 | |
| 接下来做什么、每步怎么做、步骤状态 | [实现计划](../roadmap/implementation/README.md) 和各阶段文件中该步骤的“状态” | 交接记录只写指向 |
| 当前进行到哪、交给下一位的事 | [交接记录](handoff.md) 最上面一节 | 规则文件 |
| 助手之间的问题、评审请求和答复 | 交接记录“请下一位回答”；涉及验证的结论写进验证日志 | 临时目录、直接调用另一位助手 |
| 现在能试用什么、最近一次验证 | [预览说明](window-system-preview.md) | 设计文档 |
| 每一轮做了什么、跑了哪些检查、结果和数字 | [验证日志](verification-log/2026-10.md)（按月分文件） | 规范、设计、计划正文 |
| 用户能感觉到的版本变化 | [CHANGELOG.md](../../CHANGELOG.md) | |
| 踩过的坑和排查方法 | [开发经验](lessons/README.md) | 规范正文（规范只写规则） |
| 模块怎么构建、怎么接入 | 各模块目录的 `README.md` | 用户指南 |
| 用户怎么写 Lua 脚本、默认上限 | [Lua 使用说明](lua-guide.md) | 模块 README 只链接 |
| 第三方组件与许可 | [THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md) | |
| 以后再做的事 | [未来规划](../roadmap/future-plans.md) | 设计文档 |
| 业务功能对标 | [业务功能对标](../roadmap/feature-parity-plan.md) | |

写法：

- 规范、设计、计划写现在的规则和要求，不写历史，也不写没人维护的版本号和日期（改动历史看 git 和验证日志）；需要时开头用一行“状态”说明文档性质，例如“设计要求，尚未实现”。
- “某日修订”“此前的做法被取代”这类经过写进验证日志，正文直接写成现行规则。
- 状态只在一个地方维护：步骤状态在实现计划，当前位置在实现计划的“当前位置”一行，交接记录和预览说明只链接或写一句结论。
- 数值（尺寸、上限、版本号）只写在权威位置，别处写“见……”。
- 本仓库公开，任何文档都不写本机的路径、已装软件、用户名等配置。
- 对外文字按本地 `shuorenhua` skill 的要求写。

## 索引

- [文档入口](../README.md) 是总索引：`docs/` 下每一份文档或者直接列在入口里，或者列在入口指向的目录页里（[ADR 目录](../adr/README.md)、[开发经验](lessons/README.md)、[实现计划](../roadmap/implementation/README.md)、[整体审查快照](../roadmap/review-2026-10/README.md)）。
- 仓库根的 [README](../../README.md) 链接文档入口、变更记录和各模块说明。
- 新增、改名、拆分或删除文档时，在同一个提交里更新它所在的索引；删除前把仍有用的内容移到权威位置，并改掉所有指向它的链接。
- 文件名用小写英文加连字符；整体审查的快照放在 `docs/roadmap/review-<年>-<月>/`，不再更新。

## 改了什么，同步更新什么

提交前对照下表，把受影响的文档和代码放在同一个提交里。没有对应文档的改动不需要硬写。

| 改动 | 同一提交里要更新 |
| --- | --- |
| 用户能看到的行为、界面、默认设置 | 对应设计文档；预览说明“当前可试用的功能”；CHANGELOG“未发布” |
| 公开 API、命令、快捷键 | 模块 README；设置与命令设计；用户可用的部分写进 Lua 使用说明 |
| 构建、测试、部署脚本的用法 | 测试要求或工程设计中对应一节；预览说明里的命令；AGENTS.md 的常用命令 |
| 规则或协作约定 | AGENTS.md 或 CONTRIBUTING.md；交接记录“本轮新决定” |
| 长期决定 | 新 ADR 和 ADR 目录；被取代的 ADR 改状态 |
| 完成或暂停实现步骤 | 该步骤“状态”；实现计划“当前位置”；验证日志；预览说明“最近一次验证”；交接记录 |
| 修复花了明显工夫的缺陷 | 开发经验对应分类 |
| 依赖或工具链 | THIRD_PARTY_NOTICES；工程设计；相关 ADR |
| 新增、删除、移动文件或目录 | 引用它的文档和索引；工程设计 §8 的目录规划（目录层级变化时） |

## 提交前检查

1. `git diff --staged` 只含这一件事，并且上表要求的文档都在里面。
2. 运行 `pwsh tools/check-docs.ps1`：检查 Markdown 链接和锚点是否存在、每份文档能否从文档入口找到、文档里有没有本机路径。
3. 改动涉及的文档里没有留下与新状态冲突的旧说法（用 `rg` 搜一下改掉的名字、数字、命令）。
4. 目录结构整洁合理：新增或移动的文件放在合适的位置（代码按 [工程设计 §8](engineering-design.md#8-推荐目录组织) 的目录规划，文档按本文的权威位置表）；没有空目录、临时脚本、诊断残留、备份文件和不再使用的文件。
5. 顺带看本次涉及的文档是否该合并、拆分或删除，能在本次处理的就处理，否则记进交接记录。

## 接手时的审查

接手时除了核对上一位的说法（见 AGENTS.md），还要按本文审查上一位的提交：文档是否同步更新、有没有新的重复或冲突、索引是否完整、文件是否放在合适的目录、有没有留下临时文件。还要看上一位留下的目录和文件是否整洁合理（同“提交前检查”第 4 条）。发现的问题在交接记录里写明，属于上一位的步骤的就请上一位返工，零散的直接修正，并把有代表性的问题写进 [助手协作经验](lessons/collaboration.md)。
