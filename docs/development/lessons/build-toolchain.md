# 构建与工具链经验

适用于 Windows、Qt 6.12 的 MSVC 2022 套件、Visual Studio 2022（MSVC 19.44）。切换的决定见 [ADR 0009](../../adr/0009-msvc-toolchain.md)。

## MSVC

### 没有 `/utf-8` 时中文字符串会悄悄变成乱码

- **现象**：从 MinGW 切到 MSVC 后第一次构建，零错误、只有 7 个与编码无关的警告，但仍有 28 个含中文的源文件编译时没带 `/utf-8`，其中包括 `script_api.cpp`、应用的 `script_services.cpp`、`user_preferences.cpp` 和占位内容等正式代码。
- **原因**：MSVC 默认按系统代码页（中文 Windows 是 936／GBK）读取没有 BOM 的源文件。很多 UTF-8 中文字节序列在 GBK 下恰好也是“合法”的字符，编译器不会报 C4819 或 C4566，字符串就悄悄变成了乱码。原来只有几个主要的库目标加了 `/utf-8`，测试程序和其他目标没有。
- **做法**：各目录的 CMakeLists 末尾遍历本目录的编译目标（`BUILDSYSTEM_TARGETS`，只取可执行文件和库），统一加 `/utf-8`；新增目标自动覆盖，仍是目标级选项，不加全局选项。
- **验证**：读取 `compile_commands.json`，找出所有含非 ASCII 字节的源文件，确认它们的编译命令都带 `/utf-8`（修复后为 0 个缺失）。不要只看有没有编码警告。
- **出处**：2026-10-20。

### 链接用的工具集不能比任何一个被链接的二进制更旧

- **原因**：微软的二进制兼容规则：MSVC 2015 起的版本可以混用，但链接时用的工具集必须至少和构建任何一个被链接二进制（包括 Qt 的库）的工具集一样新。
- **做法**：Qt 套件在 `mkspecs/qconfig.pri` 中记录了构建它的 `QT_MSVC_MAJOR/MINOR/PATCH_VERSION`（Qt 6.12.0 为 19.44.35227）。`tools/toolchain.ps1` 读出这个版本，与本机 `cl` 的版本比较，更旧时直接报错，提示更新 Visual Studio。注意 VS 工具集目录名（例如 `14.44.35207`）不等于 `cl` 的实际版本（同一目录下是 19.44.35229），要以 `cl` 自己报告的版本为准。
- **出处**：2026-10-20。

### `cl` 的版本号输出到标准错误，和用法说明的先后不固定

- **现象**：读取编译器版本时第一次成功，第二次失败，拿到的是“用法: cl ...”这一行。
- **原因**：`cl` 不带参数运行时，版本横幅写到标准错误，用法说明写到标准输出，PowerShell 合并两路输出时先后顺序不固定。
- **做法**：在全部输出中查找版本号，不要只取第一行。
- **出处**：2026-10-20。

## CMake

### 本地化的 `cl` 让头文件依赖随控制台代码页丢失

- **现象**：改了头文件，增量构建只重编直接改动的源文件。安装后的外部宿主因结构布局不一致而崩溃；另一次同一进程里设置控件已用新常量，旧测试目标仍期待原值。`ninja -t deps <对象文件>` 显示 `#deps 0`（[标题裁切验证](../verification-log/2026-10.md#选项卡标题裁切实现与验证2026-10-23)、[长度控件记录](../verification-log/2026-10.md#标题长度滑条与可复用数值组件2026-10-23)）。
- **原因**：中文版 `cl` 的 `/showIncludes` 行以“注意: 包含文件:”开头，按控制台输出代码页编码：UTF-8 控制台写 UTF-8，管理员会话等默认 936 的控制台写 GBK。CMake 配置时检测这个前缀，却按控制台**输入**代码页解码（`execute_process(... ENCODING AUTO)` 用的是 `GetConsoleCP`），再以 UTF-8 写进 `rules.ninja` 的 `msvc_deps_prefix`；Ninja 拿它与 `cl` 的原始字节逐字节比较。两个代码页不一致，或配置和构建时的控制台不同，前缀就对不上，依赖为空且不报错。同一台机器上 Debug 目录记成了 GBK，只改输出代码页时又记成了“UTF-8 被当成 GBK 再转存”的乱码。
- **做法**：`toolchain.ps1` 的 `Enter-Toolchain` 在配置和构建期间把控制台输入和输出代码页都固定为 UTF-8，并实测当前 `cl` 的前缀；`Get-StaleBuildReason` 发现构建目录记录的前缀不同（或编译器不同）时，`build.ps1`、`verify.ps1`、`bench.ps1` 先清空该目录。已经在错误代码页下编译、依赖为空的对象不会自己恢复，发现 `#deps 0` 的普通源文件时清空那个构建目录重建。不能把链接成功当作结构布局一致的证明。
- **出处**：2026-10-23，Claude 接手审查时查明，此前两次用清理重建绕过。

### 区分 CTest 默认时限与测试的显式属性

- **现象**：为超时套件传入更长的 `ctest --timeout`，测试仍在原时限被终止。
- **原因**：`--timeout` 只提供没有显式 `TIMEOUT` 属性时的默认值，不能覆盖 `set_tests_properties` 已设置的值。
- **做法**：诊断时先用 `ctest --show-only=json-v1` 核对命令、属性和工作目录，在系统临时目录生成仅改变观察时限的清单。完成诊断不等于通过原验收；正式调整先评审，再按配置修改指定套件的属性，核对全部属性差异。
- **验证**：原负载、内部断言与逐项诊断、配置比较的记录见 [验证日志](../verification-log/2026-10.md#msvc-debug-套件总时限诊断与评审2026-10-21)。

### 换编译器时要清空构建目录

- **原因**：CMake 缓存记录了第一次配置时的编译器，换成另一个编译器后不能沿用；Debug 和 Release 是两个独立的构建目录，各自的缓存要分别判断。
- **做法**：`toolchain.ps1` 的 `Get-StaleBuildReason` 读取构建目录 `CMakeCache.txt` 中的 `CMAKE_CXX_COMPILER`，与本次使用的编译器不同时由构建脚本先清空该目录。不要用“上一次构建用的是哪套工具链”这种全局记录来判断，否则先构建 Release 后，Debug 目录会漏掉清理。
- **出处**：2026-10-20。

## 翻译提取

### 用 JSON 项目描述保留 Unicode 路径

- **现象**：相同翻译覆盖检查在普通目录通过，临时副本的路径含中文后，`lupdate` 报源文件不存在。
- **原因**：Qt 的 `@list` 输入按本地代码页解码，UTF-8 文件中的路径会损坏；给每行路径加引号也会把引号当作文件名的一部分。依据见 [Qt lupdate 源码](https://github.com/qt/qttools/blob/6.12/src/linguist/lupdate/main.cpp)。
- **做法**：使用 `lupdate -project` 的 UTF-8 JSON 项目描述传入源文件清单，保留 Unicode 路径，也避免命令行长度限制。临时夹具目录包含中文和空格，正反向用例都经同一入口。
- **验证**：`tools/tests/translations-test.py`（当时是同名的 PowerShell 脚本），经过见 [8.12 记录](../verification-log/2026-10.md#英文源文本与覆盖检查2026-10-24)。
