# 开发经验

这里记录开发中真正踩过的坑：现象不直观、原因藏在框架或平台里、下次很可能再遇到的问题。规范性要求写在 [工程设计](../engineering-design.md) 和 [测试要求](../testing-design.md)；这里写的是这些要求背后的具体教训，以及排查时用过、确实有效的方法。

## 分类

分类不预先铺满，随项目增长按需添加。经验先按“根因在哪里”归类：

- **技术类**：根因在框架、平台或工具本身，换个模块也会遇到。例如 Qt Widgets、Windows 平台；以后接入 libssh2、ConPTY、Lua、Scintilla 时，第一次遇到值得记录的问题就新建对应文件。
- **模块类**：根因在某个模块自己的设计或约定，只在这个模块里有意义。例如以后的 SSH 会话、SFTP、终端；文件名用 `module-<模块名>.md`，模块改名或拆分时一起调整。
- **流程类**：测试、调试、构建、版本控制等跨模块的做法。

一条经验同时涉及多类时，写在根因所在的分类，其他分类用一句话加链接引用。某个文件超过约 300 行或主题明显分成几块时，拆成更细的文件（例如 `qt-widgets.md` 拆出 `qt-popups.md`），并保留原链接的去向。

新增、拆分或删除分类时，同步更新下表和 [文档入口](../../README.md)。

| 文档 | 类型 | 内容 |
| --- | --- | --- |
| [Qt Widgets](qt-widgets.md) | 技术 | 原生子窗口、弹出菜单、滚轮事件、工具提示、样式表 |
| [Windows 平台](windows-platform.md) | 技术 | 非客户区命中测试、Snap 浮窗、系统提示、DPI 虚拟化、窗口句柄 |

## 怎么写一条经验

每条经验一个三级标题，标题直接写结论，读者只看标题也知道该怎么做。正文按下面的顺序，没有内容的项可以省略：

- **现象**：用户看到了什么，在什么操作之后出现。
- **原因**：根因，写到框架或平台的具体机制；引用 Qt 或 Windows 的行为时写清版本。
- **做法**：以后写代码时怎么避免；能写成一句规则的就写成规则。
- **验证**：哪个测试守住它，测试是否确认过在旧代码上会失败。
- **出处**：日期、提交、测试名。

写作要求：

- 只记录有证据的结论。推测写成“推测”，排除过的假设可以简短写出，省得下次重复排查。
- 同一个问题只写一处，其他分类用链接引用。
- 经验过时（例如 Qt 升级后行为改变）时直接修改或删除，并在出处里注明。

## 什么时候写

修完一个缺陷、或排查花了明显的工夫时，在同一个提交里补上对应经验。判断标准：如果下次遇到同样的现象，这条记录能不能省掉大部分排查时间。普通的笔误和一眼就能看出原因的问题不用记。
