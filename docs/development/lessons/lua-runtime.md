# Lua 运行时

### 用户钩子内部也必须保留停止检查

**现象**：开放 `debug.sethook` 后，用户可以替换运行时的计数钩子。即使把两种钩子合并，如果用户钩子本身进入死循环，普通的计数检查仍不能停止它。

**原因**：Lua 5.5.1 在执行钩子期间把 `lua_State::allowhook` 清零，避免递归触发钩子。用户钩子中的 Lua 指令因此不会再进入运行时的停止检查。仅包装 `debug.sethook` 或 `pcall` 不够；开放 `debug` 后，脚本还能取出包装函数的原始上值。

**做法**：运行时始终安装 C 分发钩子，先检查粘滞的停止状态，再分发用户事件。正常状态只保留计数与用户请求的事件；发现停止后才增加调用／返回事件并缩短计数间隔，避免原始 `pcall` 反复吞掉错误，也避免每次普通函数调用进入 C。用户记录用注册表弱键保存，不延长协程生命周期。执行用户钩子时，用 RAII 暂时允许 C 分发钩子重入；重入路径只检查停止，不递归调用用户钩子。退出用户钩子时恢复状态，包括 Lua 的 C++ 异常路径。用户协程可能在取消后继续被全局变量持有，新任务恢复它时须按用户记录恢复正常掩码和间隔。

用户计数与运行时间隔取最大公约数，再按用户自己的计数累计；只取较小值会让不整除的计数提前触发。关闭解释器和清理协程时不再执行用户钩子。

此处私有依赖固定版本的 `lstate.h`，不进入公开头文件，不修改上游源码。升级 Lua 时必须复核 `allowhook`、钩子异常展开和停止用例。

**验证入口**：`modules/lua-runtime/tests/script_runtime_test.cpp` 中实际钩子掩码、取消后保留协程恢复、用户钩子、用户钩子内部循环、原始 `pcall`、弱引用及终结函数用例。原来的恶劣循环场景保留，改由显式停止请求触发。实际运行结果与前后基准见 [验证日志](../verification-log/2026-10.md)。

**出处**：2026-10-20，阶段 9.8；[ADR 0002](../../adr/0002-lua-as-cxx-with-gc-hook.md)、[ADR 0008](../../adr/0008-full-standard-library-for-local-scripts.md)。

### 阻塞 C 调用返回前，线程和解释器必须继续存活

**现象**：开放 `os.execute` 等标准调用后，关闭窗口不能再无限等待 Lua 线程；简单地超时后销毁线程或解释器，又会让仍在执行的 C 调用访问已销毁对象。

**原因**：Lua 钩子只在 Lua 检查点运行，无法安全地中断阻塞 C 调用。原来的阻塞式跨线程关闭与无限 `wait()` 只在执行时间受限的假设下看起来可行。

**做法**：退出时原子地设置停止和代次，排队关闭 worker，最多等待 1900 ms。未返回的 worker、VM、分配统计和无 parent 的 `QThread` 继续存活；C 调用返回后，在下一检查点停止，worker 关闭 VM 并退出线程，再按 Qt 线程结束规则删除。已销毁的 facade 不再接收回复。不能强杀线程，也不能先释放分配器统计。

**验证入口**：运行时的阻塞重置和析构用例，以及应用的独立子进程退出用例。测试子程序先写 ready 文件确认已进入阻塞调用，再开始测量退出耗时；正常的三秒标准调用也必须成功，防止把超时中止误当作修复。

阻塞测试的释放文件必须保留到辅助进程确认结束。曾在 scope guard 写出释放文件后立即删除临时目录，辅助进程轮询错过了这个瞬时文件，继续等待并持有继承的 CTest 输出句柄：Qt 用例报告约 13 秒，CTest 却等待约 58 秒。现在先持有辅助进程句柄，写释放信号后等待其退出，再清理目录；保留原来的负载和 60 秒套件阈值。完整进程退出耗时由父子共享的单调时钟测量，不能只测脚本服务的析构。

**出处**：2026-10-20，阶段 9.8。

### 操作另一个协程的栈前先预留空间

**原因**：当前 C 函数能使用的栈余量不代表目标协程也有余量。Lua 5.5.1 的 `ldblib.c` 在跨状态压栈前显式检查目标栈；自定义 `debug.sethook`／`gethook` 包装也必须遵守，不能直接在目标状态上 `lua_pushthread`。

**做法**：跨状态访问前调用 `lua_checkstack(target, 1)`；失败在当前调用状态报告错误。测试使用内部夹具填满目标协程已分配的栈，再真实调用两个包装，检查原有值保留且目标容量扩展。这样能检出 Release 构建中写进保留余量、尚未崩溃的遗漏。

**验证入口**：`explicitCoroutineHooksReserveStackSpace` 的 `sethook`、`gethook` 两个数据行。私有 Lua 状态只供内部测试访问，不进入公开 API。

**出处**：2026-10-21，阶段 9.8 独立代码审查。

### 标准 require 的模块初始化不能跨 C 加载器让出

**现象**：用户协程中的 `muxora.*` 可以让出等待宿主，但在 `require` 直接执行的模块顶层调用时会失败。

**原因**：Lua 标准 `require` 经 C 加载器执行模块，当前调用链不可让出。只给协程的 `resume` 转发宿主标记，不能改变这条 C 调用链。

**做法**：保留标准 `require` 的缓存与搜索规则；模块返回初始化函数，在 `require` 返回后调用。宿主桥接先检查当前状态能否让出，拒绝时不能已经提交请求或产生 GUI 副作用。用法见 [Lua 指南](../lua-guide.md)。

**验证入口**：`modules/window-system-lua/tests/script_host_test.cpp` 的模块缓存、返回初始化函数及不可让出时无副作用检查。

**出处**：2026-10-20，阶段 9.8。
