# 助手协作经验

Claude 和 Codex 轮流开发时，在交接和互相审查中发现的问题。规则见 [AGENTS.md · 助手交替开发](../../../AGENTS.md#助手交替开发)。每条写清是哪一轮发现的，方便以后对照。

## 实现

### 改动运行时热路径前后都要测性能

- **现象**：9.8 让运行时为所有脚本始终安装“函数调用和返回”钩子。2026-10-21 接手审查时实测：2000 万次函数调用从 0.44 秒变成 1.42 秒，慢约 3.2 倍；没有函数调用的纯循环不受影响。交接和验证记录里没有任何性能数据。
- **原因**：这个钩子是为了一种极端情况（脚本用调试接口取出原始 `pcall`，在循环里反复吞掉停止请求），代价却落在所有脚本上。改动时只测了功能，没有测热路径的耗时。
- **做法**：改动每次调用、每帧、每次按键都会经过的代码（脚本运行时、布局刷新、绘制、按键分发）时，在同一台机器上对比改动前后的耗时，把数字写进验证日志；变慢的部分要么去掉，要么限制在真正需要的场景（这里是：收到停止请求后才加装调用钩子）。性能基准见 [测试要求](../testing-design.md)。

### 实现达不到用户定下的要求时，交给用户决定，不要写成“用法”

- **现象**：ADR 0008 写明本地脚本“与 Neovim 一致”。9.8 实现后，被 `require` 加载的模块不能在顶层调用 `muxora.*`（标准 `require` 由 C 实现，模块顶层不能把控制权交给宿主），实现方把它写成了 Lua 指南里的用法（“模块返回初始化函数”）和一条开发经验，没有问用户。Neovim 的插件在 `require` 时就能调用 `vim.api`。
- **做法**：发现做不到设计或 ADR 写明的要求时，在交接记录“待用户决定”里写清差距、原因和可选方案，并在对话中提出；不要自己降低要求再把限制写成文档。这一处其实有解法：用 Lua 实现一个行为等同标准的 `require`（同样使用 `package.searchers`、`package.loaded`），模块代码由 Lua 调用，就能在顶层调用宿主。

## 验证

### 改完入口脚本，要用文档里写的实际调用方式跑一遍

- **现象**：重写后的 `quiet-desktop.ps1`，按 AGENTS.md 和测试要求里写的方式调用（`quiet-desktop.ps1 pwsh tools/build.ps1 -Configuration Release -Test`）根本跑不起来。原因有两个：
  - PowerShell 按前缀匹配参数，被测命令里的 `-Test` 被当成了脚本自己的 `-TestCommand` 参数；
  - 解析被测程序时，`Get-Command` 找到两个同名程序，把两个路径拼成一个字符串去执行。

  交接时写的是“完整原生路径未复跑”，而脚本自带的自测只覆盖窗口收起和恢复，没有覆盖真实的调用方式。
- **做法**：
  - 交出前，至少按文档里的写法真正跑一次入口脚本；
  - 自测要覆盖实际调用方式（被测命令带 `-Test` 等参数、程序名有多个同名结果）；
  - 不能跑的部分不要留给下一位，除非确实被环境挡住，并写明原因。

### 验证结论按“一次运行、一个代码版本”来写

- **现象**：9.8 的交接把“首次全量 57/61”“之后只重跑的若干套件”“各套件最新报告共 2343 行通过”放在一起，而这些报告来自不同的代码版本，中间还改写了测试脚本。最终代码其实没有完整跑过一次全量。
- **做法**：只重跑失败项是允许的（AGENTS.md），但结论要写清每个数字对应哪次运行、哪个提交。最后又有较大改动时（这次是重写测试入口脚本），要再跑一次全量，才能写“全部通过”。

## 规则与配置

### 规则从仓库移到个人配置时，两位助手都要同步

- **现象**：用户让 Codex 把“默认用 pwsh”“提权优先用 gsudo”两条规则从 AGENTS.md 移到 Codex 的全局配置。Claude 看不到 Codex 的全局配置，接手时发现规则不见了。顺带发现 Codex 全局配置里有一条和项目规则正好相反的 git 规则（原意写反了）。
- **做法**：属于这台电脑、而不属于项目的约定，放进每个助手各自的全局配置（Codex 的 `~/.codex/AGENTS.md`、Claude 的 `~/.claude/CLAUDE.md`），内容保持一致，并在交接记录里说明移动了什么。两边全局配置不一致时，以用户确认的说法为准，同时改两边。
- **出处**：2026-10-21，用户确认后两边已同步。
