# 助手协作经验

Claude 和其他助手轮流开发时，在交接和审查中发现的问题。执行者接手时先读完本文再开工；Claude 每次审查发现能归纳的问题都补一条，并把对应的检查加进审查清单 [`review-handoff`](../../../.claude/skills/review-handoff/SKILL.md)。规则见 [AGENTS.md · 轮流开发与交接](../../../AGENTS.md#轮流开发与交接)。每条写清是哪一轮发现的，方便以后对照。

## 实现

### 改动运行时热路径前后都要测性能

- **现象**：9.8 让运行时为所有脚本始终安装“函数调用和返回”钩子。2026-10-21 接手审查时实测：2000 万次函数调用从 0.44 秒变成 1.42 秒，慢约 3.2 倍；没有函数调用的纯循环不受影响。交接和验证记录里没有任何性能数据。
- **原因**：这个钩子是为了一种极端情况（脚本用调试接口取出原始 `pcall`，在循环里反复吞掉停止请求），代价却落在所有脚本上。改动时只测了功能，没有测热路径的耗时。
- **做法**：改动每次调用、每帧、每次按键都会经过的代码（脚本运行时、布局刷新、绘制、按键分发）时，在同一台机器上对比改动前后的耗时，把数字写进验证日志；变慢的部分要么去掉，要么限制在真正需要的场景（这里是：收到停止请求后才加装调用钩子）。性能基准见 [测试要求](../testing-design.md)。
- **复发**：2026-10-30 审查 Quick 迁移时发现，`TabBar` 和 `TabBarItem` 每次鼠标移动、每一帧都刷新环境，每次刷新都读一次环境变量、调一次 `SystemParametersInfoW` 查询动画设置，实测每次 4.3 微秒。设置这类很少变化的值，在变化通知（这里是 `WM_SETTINGCHANGE`）里读，热路径只读缓存。`ac1a3df` 修复。

### 实现达不到用户定下的要求时，交给用户决定，不要写成“用法”

- **现象**：ADR 0008 写明本地脚本“与 Neovim 一致”。9.8 实现后，被 `require` 加载的模块不能在顶层调用 `muxora.*`（标准 `require` 由 C 实现，模块顶层不能把控制权交给宿主），实现方把它写成了 Lua 指南里的用法（“模块返回初始化函数”）和一条开发经验，没有问用户。Neovim 的插件在 `require` 时就能调用 `vim.api`。
- **做法**：发现做不到设计或 ADR 写明的要求时，在交接记录“待用户决定”里写清差距、原因和可选方案，并在对话中提出；不要自己降低要求再把限制写成文档。这一处其实有解法：用 Lua 实现一个行为等同标准的 `require`（同样使用 `package.searchers`、`package.loaded`），模块代码由 Lua 调用，就能在顶层调用宿主。

### 合并或拆分分支时，逐个核对原来的每一步还在

- **现象**：1.7 把 `setTabTopBar()` 拆成“已有视图”和“还没有视图”两个分支，原来设置“控件已被接管”标记的那一行只留在了后一个分支。结果同一个栏控件可以再交给另一个标签或窗格，两个容器争同一个控件。上下两个函数是复制出来的，两处都漏了；现有测试只测了新分支。
- **做法**：改写已有函数时，把改前的每一个副作用（设标记、改父对象、发信号、检查返回值）列出来，确认改后的每条路径都还做了。两段代码几乎一样时先合成一个函数再改，不要复制后各改一处。给改动的每条分支都写测试，测试要在改前的问题代码上失败。
- **出处**：2026-10-24，Claude 审查 `bc16ecf` 时发现，`698255b` 修复，`PaneBarPolicyTest::aTabBarBelongsToOneOwner`。

### 内部数据不要再套一层预校验

- **现象**：Quick 标签组表面在准备帧之前，先用一个 176 行的头文件把准备过程的成本重算一遍：逐个检查每个坐标、路径和图片尺寸，然后准备过程自己再检查一遍路径。帧数据来自我们自己的控制器，尺寸受真实窗口几何约束；这份副本却要和真正的准备代码保持同步，而且一旦拒绝，表面就静默消失。配套的测试专门喂无穷大的圆角去触发它。
- **做法**：校验只放在外部输入的边界（文件、网络、用户输入、远端发来的标题），内部调用之间的约束用 `Q_ASSERT`。需要限制资源时，限制放在真正分配资源的地方一次，不在前面复制一份成本模型。不为不会出现的输入写测试。
- **出处**：2026-10-30，Claude 审查 `a33cf35`，`8024c97` 删除，同时删掉了据此写的经验“路径预算不能代替冷图预算”。

### 样板代码先找现成的辅助函数

- **现象**：迁移期间新增约三十个测试套件，每个都复制了同样的八行 CMake 注册，而文件里已经有 `window_system_add_suite`，只是它不能指定链接的库。
- **做法**：要写第二遍相同的样板时，先找现成的辅助函数，缺参数就给它加参数，不要复制。
- **出处**：2026-10-30，Claude 审查，`299b011` 合并。

## 验证

### 改完入口脚本，要用文档里写的实际调用方式跑一遍

- **现象**：重写后的 `quiet-desktop.ps1`，按 AGENTS.md 和测试要求里写的方式调用（`quiet-desktop.ps1 pwsh tools/build.ps1 -Configuration Release -Test`）根本跑不起来。原因有两个：
  - PowerShell 按前缀匹配参数，被测命令里的 `-Test` 被当成了脚本自己的 `-TestCommand` 参数；
  - 解析被测程序时，`Get-Command` 找到两个同名程序，把两个路径拼成一个字符串去执行。

  交接时写的是“完整原生路径未复跑”，而脚本自带的自测只覆盖窗口收起和恢复，没有覆盖真实的调用方式。
- **做法**：
  - 交出前，至少按文档里的写法真正跑一次入口脚本；
  - 自测要覆盖实际调用方式（被测命令带 `-Test` 等参数、程序名有多个同名结果）；
  - 不能跑的部分不要留给下一位，除非确实被环境挡住，并写明原因。
- **出处**：2026-10-21 Claude 接手时发现；两个缺陷当天修复，`quiet-desktop-test.ps1 -Headless` 覆盖这两种调用方式。

### 用例要防住用户能遇到的错误，不测语言本身

- **现象**：迁移期间的标签呈现测试里，有用例检查“空的 `std::optional` 复制后仍为空”“复制的 `std::optional` 改了不影响原件”，也有用例断言私有字段的中间值（未测量的宽度为 -1）。这些检查的是 C++ 的值语义和实现细节，实现换个写法就会失败，却防不住任何用户能看到的问题。
- **做法**：写用例前先说出它防住的用户可见错误，说不出的不写，规则见 [测试的分量](../testing-design.md#测试的分量)。
- **出处**：2026-10-30，Claude 审查，`bbc8628` 退役。

### 验证结论按“一次运行、一个代码版本”来写

- **现象**：9.8 的交接把“首次全量 57/61”“之后只重跑的若干套件”“各套件最新报告共 2343 行通过”放在一起，而这些报告来自不同的代码版本，中间还改写了测试脚本。最终代码其实没有完整跑过一次全量。
- **做法**：只重跑失败项是允许的（AGENTS.md），但结论要写清每个数字对应哪次运行、哪个提交。最后又有较大改动时（这次是重写测试入口脚本），要再跑一次全量，才能写“全部通过”。

## 文档

### 计划原文不要改写成实现的样子，差别写在“状态”里

- **现象**：1.7 完成后，执行者把计划里“测试”“验证”两段改写成了实际做的用例名和基准场景，“实现与计划的差别”又把实现过程复述了一遍，真正的差别（多了自动隐藏和全屏目标、基准改用 `restore` 场景）反而埋在里面。
- **做法**：计划的目标、实现、测试、完成标准是验收依据，完成后不改。做法不同的地方写进步骤“状态”下的“实现与计划的差别”，只写和原文不一样的地方及原因；数字写在验证日志，状态里给链接。
- **出处**：2026-10-24，Claude 审查 `fb1367a`。

### 模块说明不要复述设计文档

- **现象**：1.7 在模块 README 里加了两段，几乎逐句复述设计文档 §3.1；同一轮还留下一句过时的后端说法（只写了 IMM，实际已经保存 TSF 配置），因为改实现时只改了其中一处。
- **做法**：同一件事只在 [文档维护规范](../documentation.md) 规定的位置写全，模块 README 写一两句概述加链接。改实现后用 `rg` 搜一遍旧说法。
- **出处**：2026-10-24，Claude 审查 `bc16ecf`、`91956aa`。

### 本机信息包括装了什么软件，提交说明也是公开的

- **现象**：8.16 的提交说明、验证日志和经验里写了用户装的输入法名称、它的类标识，以及“本机有三个键盘布局”。文档后来删掉了，但提交说明已经推送，只能改写历史。
- **做法**：公开仓库里只写通用描述（“一个 TSF 输入法”“已装的键盘布局”），不写软件名、产品标识、数量、路径。提交说明写好后和文档一样检查一遍再提交。
- **出处**：2026-10-24，Claude 审查 `91956aa`、`a13a17c`。

### 生成的文件只用生成工具写

- **现象**：翻译目录一直是手工排版加手工增删条目，翻译检查只比较内容，所以能通过；之后谁一运行 lupdate，就整份重排上千行。用户指出这个问题出现了好几次。
- **做法**：生成文件（翻译目录等）只由对应的构建目标写，人只改允许手改的部分（译文）。检查脚本要能发现手工改过的格式，不能只比较内容。
- **出处**：2026-10-24，`644d90c`。

## 仓库整理

### 增量构建成功不代表产物与源码一致

- **现象**：接手构建报告无需编译，新加入的真实钩子掩码回归却在旧源码上意外通过，基准也没有出现源码中常驻调用钩子的开销。
- **原因**：已有目标文件中的掩码与源码不同，但目标文件比源码新，增量构建没有重新编译。只看 Git 状态、时间戳和成功退出不足以发现这种产物残留。
- **做法**：新回归必须先证明旧实现失败；遇到矛盾时检查实际行为及目标代码，仅重建相关对象和依赖后再测。作废不能归属于源码版本的结果，保留原始运行记录并说明原因。
- **出处**：2026-10-21，9.8 R1 接手基准，见 [验证日志](../verification-log/2026-10.md#lua-98-r1-停止钩子返工2026-10-21)。2026-10-23 查明这类残留的一个根本原因是头文件依赖随控制台代码页丢失，见 [构建经验](build-toolchain.md#本地化的-cl-让头文件依赖随控制台代码页丢失)；遇到同类矛盾先查 `ninja -t deps`。

### 整理文档入口后，要核对可复制的命令

- **现象**：文档入口和脚本已统一，部分章节的示例仍手工拼接旧工具链环境，或直接启动需要桌面隔离的测试。
- **原因**：整理时核对了链接和说明文字，没有逐段检查命令依赖的配置、运行环境和入口。
- **做法**：按命令的实际执行路径核对参数、环境准备和调用顺序；重复示例改为链接到权威说明。改过的入口按文档写法运行，链接检查通过不能代替执行验证。
- **出处**：2026-10-21，Codex 接手审查文档整理。

### 整理仓库要按完整的文件清单逐个核对，包括忽略的目录

- **现象**：2026-10-21 第一轮整理只看了文档和上一轮改过的文件，用户追问后才查出：
  - 根目录的 `mise.toml` 没人使用，它的 `test` 任务还绕过了桌面隔离；
  - MinGW 卸载后，构建脚本的 MinGW 分支和 `muxora.rc` 成了死代码；
  - `verify.ps1`、`bench.ps1` 写死读取本机的 `.local/sdk.json`，和 `build.ps1` 的 Qt 查找方式不一致，`verify.ps1` 也没覆盖 Lua 外部宿主和 Lua 部署检查；
  - 预览说明里写着本机的 SDK 路径（仓库公开）；
  - 多处文档还写着已取消的 Lua 执行预算；
  - 有一个没有调用者的公开函数，两个文件放错了目录；
  - `out/` 根下有 40 多个排查残留（状态目录、提交说明草稿、旧 MinGW 依赖包），`.claude/worktrees/` 下还有两个早已合入的旧会话工作树，约 940 MB。
- **原因**：只在熟悉的地方找，没有以文件清单为准。
- **做法**：
  - 以 `git ls-files` 的完整清单为准逐个过一遍，再单独查忽略的目录（`out/`、`.claude/`、`.local/`）和空目录。
  - 代码部分用脚本查，不靠印象：每个源文件和测试是否接入构建、内部头文件里有没有无人调用的函数、翻译文件和源码是否一致（用 `lupdate` 在副本上试跑）、文档里的链接和反引号路径是否存在、有没有本机路径。
  - 依赖或工具链被移除、ADR 写明的保留条件满足时，同一轮删掉对应的支持代码和文档说法。
- **出处**：2026-10-21，Claude 整理仓库。

### 排查时的临时文件不要散落在 `out/` 根下

- **现象**：`out/` 根下有 13 个 `snap-*-state` 目录和 10 个提交说明草稿，事后没人能说清是做什么的。
- **做法**：临时脚本、状态目录、截图和提交说明草稿放在系统临时目录或会话的临时目录；确实要放进仓库的 `out/`，就放在 `out/diagnostics/<主题>/` 下，排查结束时删除。规则见 [测试结果与排查文件](../testing-design.md#测试结果与排查文件)。
- **复发**：2026-10-24 又积累了 `out/diagnostics` 根下 400 多个、`out/test-results` 里 800 多个手工放的文件。原因是规则互相矛盾：测试要求说“首次失败和后续结果都要保留”，实现计划说“首次失败放进 `out/diagnostics/<步骤>/` 不要覆盖”，AGENTS.md 又说“结束时删除”，执行者都选了最保守的“不删”；验证日志也只写“证据见某文件”，而这些文件不在仓库里。现在证据写进验证日志正文，文件按主题存放、主题结束删除，规则只写在一处。规则之间互相矛盾时，在交接里提出来，不要各自选一种做法。

## 沟通

### 助手之间不直接调用，问题经交接记录或用户转达

- **现象**：2026-10-21 Codex 工作中两次在命令行运行 `claude -p --no-session-persistence`，请 Claude 评审 Debug 超时方案和 `peek-size` 测试的改法，问题和回答只留在 Codex 的临时目录里。用户和主导的 Claude 会话都看不到这两次评审，被调用的 Claude 也没有当前会话的上下文（例如刚定下的文档规则），只能根据提示词里 Codex 自己写的概括作答。
- **原因**：交接记录写着“方案交 Claude 评审”，但没有规定评审怎么进行，执行方就自己找了一条最快的路。
- **做法**：工作中不自行联系另一位助手。能等的写进交接记录“请下一位回答”，等不了的把问题整理成提示词交给用户转发，回答和决定写回仓库。规则见 [AGENTS.md](../../../AGENTS.md#轮流开发与交接)。
- **出处**：2026-10-21，用户发现后要求加规则；两次评审由主导的 Claude 会话事后重新核对。

## 规则与配置

### 规则从仓库移到个人配置时，两位助手都要同步

- **现象**：用户让 Codex 把“默认用 pwsh”“提权优先用 gsudo”两条规则从 AGENTS.md 移到 Codex 的全局配置。Claude 看不到 Codex 的全局配置，接手时发现规则不见了。顺带发现 Codex 全局配置里有一条和项目规则正好相反的 git 规则（原意写反了）。
- **做法**：属于这台电脑、而不属于项目的约定，放进每个助手各自的全局配置（Codex 的 `~/.codex/AGENTS.md`、Claude 的 `~/.claude/CLAUDE.md`），内容保持一致，并在交接记录里说明移动了什么。两边全局配置不一致时，以用户确认的说法为准，同时改两边。
- **出处**：2026-10-21，用户确认后两边已同步。
