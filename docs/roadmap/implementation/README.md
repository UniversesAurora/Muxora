## 推荐执行顺序

阶段和步骤的编号是固定 ID（提交说明、ADR、验证日志都按编号引用），按计划写成的先后排列，**不代表执行顺序**。实际按下面的里程碑推进：前一个里程碑的步骤是后一个的前置，同一里程碑内按列出的先后做，标明“可并行”的可以各开一个会话、各用自己的 worktree（仍要遵守下文“容易冲突的文件”）。排序依据是各步骤写明的前置条件，以及“后面会用到的基础先做，避免返工”。

**当前位置**：阶段 0、1.1–1.6 完成，工具链使用 MSVC；M1 的 [9.8](phase-9-lua-extension-api.md#98-本地脚本使用完整标准库与-neovim-一致) 返工代码及相关回归完成，细分状态见该步骤。下一步是 Release 全量与部署，之后排查交接记录中的 Debug 问题；不提前进入 1.7。每完成或暂停一个步骤都更新本行，详细交接见 [交接记录](../../development/handoff.md)。

### M1 收尾与快速见效

1. **9.8 本地脚本使用完整标准库**：没有前置，用户要求尽快；要在 9.0、9.1 之前做，9.1 沿用它的宿主让出标记。
2. **1.7 非活动标签按需创建视图**：终端这类重内容的前置（阶段 7 的“阶段约束”）。可与 9.8 并行（文件不重叠）。
3. **1.10 命令注册表 ID 索引**、**1.9 布局保存移出 GUI 线程**：独立的小步骤，1.9 先看基准数据决定做多少。可与 1.7 并行，但 1.10 改 `window_manager.cpp`，不与其他改该文件的步骤同时进行。
4. **8.1 → 8.2 窗口缩放区移到外侧边框、临时面板八向调整**：8.2 是用户要的功能，必须在 8.1 之后（面板贴窗口边缘时两者抢同一块区域）。只改原生框架和停靠代码，可与 9.8、1.7 并行。
5. **6.1 应用入口拆分**：在 9.8 之后做（两者都改 `src/app`），在 4.4、7.x、9.0 往 `main.cpp` 加更多内容之前做，越早越省事。
6. **工具链决定**：已完成（2026-10-20）。Release 改用 MSVC，见 [ADR 0009](../../adr/0009-msvc-toolchain.md)；6.4、6.6、7.1、7.5、8.7 按 MSVC 进行。MinGW 套件在 MSVC 构建经过试用后由用户卸载。

4. **8.7 改用 Windows 系统通知**：没有前置，可与本里程碑任何步骤并行；按 MSVC 使用 C++/WinRT（M1 已改用 MSVC）。
5. **8.8 空工作区**：在 2.4 之后。**8.11 界面字体渲染核查**：在 2.5 之后，用组件画廊逐组件检查 ClearType 开关两种情况。

## 每个步骤的执行规则

执行任何步骤的 Agent 必须遵守下面的流程。仓库规则以 [AGENTS.md](../../../AGENTS.md) 为准，这里是落到每一步的具体做法。

### 开始前

1. 读 `AGENTS.md`、本文件、所在阶段文档的“阶段约束”和目标步骤全文。
2. 读步骤“涉及文件”里列出的全部源文件，确认文档中的行号、函数名仍然存在。若代码已经变化导致步骤描述不成立，先在阶段文档里修订该步骤，再实现；不要按过时描述硬改。
3. 确认前置步骤已经合入当前分支（看 `git log` 和阶段文档中的“状态”）。
4. 从 `main` 开新分支或 worktree，分支名 `<阶段>.<步骤>-<短名>`，例如 `1.4-tab-view-reuse`。

### 实现中

- 一个步骤一个提交（必要时可以拆成“重构无行为变化”和“行为变化”两个提交）。不要顺手修改步骤范围外的代码；发现的问题写进阶段文档的“发现”小节或审查记录。
- 公开 API 的改动必须同步：头文件注释、`modules/window-system/README.md` 或相应模块 README、外部宿主夹具（`modules/window-system/tests/fixtures/external-host/`）中至少一处真实调用。
- 新增用户可见文字使用 `QCoreApplication::translate("WindowSystem", ...)`（模块）或 `"Muxora"`（应用），并运行 lupdate 目标（`window_system_lupdate`、`muxora_lupdate`）后补全 `zh_CN` 与 `en` 两个 `.ts` 文件。
- 新增公开操作要同时提供：命令注册表中的命令（菜单、命令面板、快捷键共用）、必要的键盘方式、Lua API（如果该领域已有 Lua 分组）、自动化测试。
- 不改 Release 默认编译选项和固定部署目录 `out/package/muxora-preview/`。新增的可选构建开关默认关闭。

### 界面标准

凡是涉及界面的步骤（新增或修改控件、弹窗、页面、菜单、颜色、尺寸、交互），都按下面的标准执行，不能做成“能用就行”的原型：

- 外观与交互以 Visual Studio、VS Code 为参照，遵守 [界面设计规范](../../design/ui-design-system.md)；颜色只使用 [主题系统](../../design/theme-system-design.md) 的颜色 ID（阶段 2.3 之前使用 `Theme` 令牌），不写具体颜色值。
- 同一类界面只用一种组件：选择与单值输入用快速输入（8.4），确认用统一对话框（8.6），通知用 Windows 系统通知（8.7，不做通知中心和程序内提示）。不新建 `QDialog`、`QInputDialog`、`QMessageBox`，不调用 `exec()`。
- 每个界面步骤完成时：
  1. 在浅色、深色、黑色三个主题下截图（阶段 2.5 之后用组件画廊导出），放到 `out/diagnostics/ui-review/<步骤>/`；
  2. 对照设计规范逐条检查尺寸、间距、颜色 ID、各状态、键盘路径、焦点返回、`Esc`、文案，把检查结论写进步骤状态；
  3. 自动化测试覆盖键盘路径、焦点返回和关键几何。
- 截图和测试不等于真实桌面试用；预览说明中如实写明试用范围。

### 验证

| 场合 | 必须执行 |
| --- | --- |
| 每个步骤 | 步骤中列出的“相关套件”；新增测试在修复前失败（缺陷修复类）或覆盖新行为 |
| 性能类步骤 | 阶段 0.1 基准在改动前后各跑一次，结果写入 `out/test-results/bench-<步骤>-before.json`、`-after.json` |
| 一组步骤集中完成后 | 一次 Release 全量，使用 [测试要求 §3](../../development/testing-design.md#3-工具与统一入口) 的桌面隔离入口 |
| 改了公开 API 或安装导出 | [完整验证入口](../../development/window-system-preview.md#开发环境) 中的独立模块与外部宿主部分 |
| 改了应用行为 | `-Package` 更新固定部署目录，再经桌面隔离运行 `tools/tests/application-exit-test.ps1 -PackageDirectory <固定目录>` |

构建与完整验证命令见 [预览说明 · 开发环境](../../development/window-system-preview.md#开发环境)，筛选套件与直接使用 CTest 的方式见 [测试要求 §3](../../development/testing-design.md#3-工具与统一入口)。需要自行准备环境时，共用 [工程设计 §6.1](../../development/engineering-design.md#61-qt-sdk-的安装版本绑定与升级) 中的 `tools/toolchain.ps1`，不手工拼接 Qt 或编译器路径。单独运行会显示窗口的 Qt 测试程序也通过桌面隔离入口；其 `-o` 可将文本报告写到本次排查的主题目录。

**失败处理**：按 [测试要求](../../development/testing-design.md)：不删用例、不跳过、不改预期、不放宽阈值。先判断是否与本步骤有关：

1. 在不含本步骤修改的基线上用同样的环境运行同一套件（`git stash` 或另一个 worktree）。
2. 基线也失败：属于既有问题。记录并单独修复（单独提交），或在阶段文档“发现”中登记后继续。
3. 只在本步骤失败：修复实现，直到原有断言通过。
4. 依赖真实桌面的套件（`native-frame`、`chrome-interaction`、`floating-panel` 等）失败时，先检查测试窗口是否被其他程序遮挡（`WindowFromPoint` 命中的窗口标题和进程），不能把遮挡造成的失败写成通过，也不能写成代码缺陷。

首次失败记录保存到 `out/diagnostics/<步骤>/`，不要覆盖。

### 完成后

1. 在阶段文档中把该步骤的“状态”改为“已完成（提交 `<hash>`）”，写一行实际验证结果。
2. 在 [验证日志](../../development/verification-log/2026-10.md) 最上面加一节（带日期的三级标题），写行为变化和真实验证范围，未执行的检查写明未执行；再更新 [预览说明](../../development/window-system-preview.md)：功能有变化时改“当前可试用的功能”表格，并改写“最近一次验证”。预览说明只写当前状态，不追加带日期的叙述。
3. 提交说明：标题一行；正文写行为变化、原因、实际验证（套件数、测试行数、失败及原因）；结尾附 `Co-Authored-By` 行（见会话中的要求）。分支只用 rebase 或快进整合，不产生合并提交。

## 步骤文档的格式

每个步骤使用同一结构，便于不同 Agent 接手：

- **目标**：做完后可以观察到的结果。
- **前置**：必须先完成的步骤。
- **涉及文件**：要读和要改的文件。
- **实现**：编号的具体做法，包括数据结构、函数签名、算法和必须保持的不变量。
- **测试**：新增或修改的测试，写到测试函数名和关键断言。
- **验证**：要运行的套件和命令。
- **完成标准**：逐条可检查。
- **风险**：容易出错的地方和处理方式。
- **状态**：未开始／进行中／已完成（提交 hash）。
