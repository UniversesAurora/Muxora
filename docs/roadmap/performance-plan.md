# 性能与内存方案

目标：在几乎不牺牲交互性能的前提下压低内存，CPU 只做必要工作，绘制尽量交给 GPU，支撑同时打开数百到上千个会话。本文针对 [代码审查记录](code-review-2026-10.md) 中的 R1–R9，给出实现顺序和验证方法。数值目标在第 6 节先做测量再定，不在这里预设成绩。

## 1. 布局变化改为增量调和

**现状**：`WindowManager::refresh()` 每次都把所有内容控件改回存储控件并隐藏，删除并重建所有 `TabContent` 的分割器和窗格框，再整棵重建每个窗口的 `DockSurface`。关一个标签，也要处理全部 N 个标签的控件。重设 parent 会触发 Show/Hide、布局失效、样式重新 polish；以后接入 GPU 终端视图（`QRhiWidget`）时，跨顶层窗口重设 parent 还会重建图形资源。

**方案**：利用模型已有的不可变树。`LayoutTree` 节点是 `shared_ptr<const LayoutNode>`，没有变化的子树保持同一指针，可以直接判断“这部分没变”。

1. `TabContent` 记住上次构建所用的 `record.panes` 指针和窗格栏集合。新树指针相同、栏集合相同就跳过重建，只更新活动窗格。
2. 指针不同时按节点 ID 调和：已有 `QSplitter` 按 `splitNodeId` 复用，只调整比例和子项；只新建确实新增的节点，只销毁确实删除的节点。
3. `refresh()` 只收起将要移动或删除的内容控件。内容 ID 所属的 Tab 和窗口都没变时，不改 parent。
4. `DockSurface` 同样按窗口的 `central`、`pinnedLayouts` 指针和组记录做比较，未变化的组控件（`GroupTabs`）复用；标签增删只改对应组的标签条。
5. 跨窗口移动只给被移动的内容改 parent。

**实施顺序**：先做第 1 步，收益最大、风险最小；再做 4；最后做 2、3、5。每一步保持现有拖拽、焦点和重入测试全部通过，并加一项“操作前后未受影响的内容控件 parent 和 QWidget 实例不变”的断言。

**注意**：`refresh()` 中“先挂回存储控件再重建”的顺序，是为了防止旧 parent 销毁时连带销毁内容。增量方案必须保留这条保证：被删除的容器在销毁前，确认其中没有存活内容。

## 2. 非活动标签的视图按需创建

**现状**：每个标签都有一个 `TabContent`，即使从未显示。上千个标签就有上千套框架控件。

**方案**：

- `GroupTabs` 对非活动标签只放一个轻量占位页（或不放页，只保留标签条数据），首次激活时再创建 `TabContent`。
- 内容控件本身由宿主创建，模块不能决定其生命周期；但可以给宿主一个“视图挂起／恢复”回调，让终端这类内容在隐藏后释放渲染资源（字形纹理、帧缓冲），只保留终端核心状态。
- 隐藏控件 Qt 本来就不绘制。终端内容还需在不可见时停止生成渲染快照，只更新模型（参见 [工程设计 §3.3](../development/engineering-design.md)）。

建议给 `WindowManager` 增加宿主可选接口，例如：

```cpp
struct ContentVisibility { PaneId pane; bool visible; };
void setContentVisibilityHandler(std::function<void(const ContentVisibility&)> handler);
```

在标签激活、窗口最小化、侧栏收起时合并通知（同一事件循环内只发一次）。

## 3. 布局模型的查找与事务成本

**现状**：

- `groupForTab()` 遍历所有组的标签列表；`tabForPane()` 遍历所有标签的窗格树；`familyHasTabs()` 为每个窗口生成完整标签列表。源码中有 60 多处调用 `groupForTab`/`tabForPane`，有些在循环里，整体会退化成 O(N²)。
- 每个事务复制整个模型（`QHash` 写时复制，修改时整份深拷贝），再做全量 `validate()`。
- 拖动分隔条时每个 `splitterMoved` 都走一次完整事务，然后在所有标签视图里 `findChildren<QSplitter*>()`。

**方案**：

1. **反向索引**：在 `LayoutModel` 中加入 `tabGroup_`（Tab→Group）和 `paneTab_`（Pane→Tab）两个可变缓存，加一个脏标记。所有私有修改函数改动标签或窗格树时置脏；查询时脏了就重建（O(N) 一次），否则 O(1)。`validate()` 增加“索引与扫描结果一致”的检查，用现有模型测试覆盖。
2. **比例修改快速路径**：`setSplitRatio()` 只改一个节点的比例，不影响其他不变量。可以单独实现：定位节点、路径复制、只校验比例范围，跳过全量 `validate()`。
3. **拖动中不提交**：`QSplitter` 拖动过程中只改控件，松开鼠标时提交一次模型（或用 0 ms 定时器合并一帧内的多次移动）。持久化本来就有 700 ms 合并，不受影响。
4. **节点到控件的映射**：`TabContent` 和 `DockSurface` 各自维护 `QHash<QUuid, QPointer<QSplitter>>`，替代 `findChildren`。
5. **去掉序列化比较**：`addTabToNewGroup()` 和 `requestCloseAllWindows()` 改为只比较 `revision()` 和控件身份；如果担心有修改路径没递增 revision，先在 Debug 构建中加断言做一段时间的对照。
6. **事务复制**：先测量。1000 个标签时一次完整复制在什么量级，测出来再决定是否需要持久化数据结构或差量回滚日志。没有数据前不要重写。

## 4. 主题从样式表转向调色板与 ProxyStyle

**现状**：`applyTheme()` 给每个顶层窗口设一整段 QSS。启用样式表后，每个子控件都要走 `QStyleSheetStyle`：内存更高、polish 更慢，内容跨窗口移动时重新解析规则；终端这类自绘内容也会被卷进去。

**方案**：

- 颜色交给 `QPalette`（`applyTheme()` 已经设置了大部分角色）。
- 尺寸和外形交给一个以 Fusion 为基础的 `QProxyStyle`，处理标签、工具按钮、滚动条、分隔条等现在由 QSS 描述的部分。
- 模块自绘的控件（标签条、边栏、工具条）直接读 `Theme` 令牌，不再依赖样式表。
- 宿主内容默认不受模块样式影响；需要统一外观时读 `Theme` 或调色板。

逐个控件迁移，迁移一个删一段 QSS；每步用现有像素和几何测试守住外观。

**限制（实现计划阶段补充）**：`theme.cpp` 中 `styleSheet()` 的注释说明，`QWidget::setStyle()` 只作用于单个控件，不随子控件增加和改挂传播；整棵控件树使用同一个样式只能靠 `QApplication::setStyle()`，而模块契约是不改变应用级样式。因此迁移只能作为宿主可选的应用级入口，模块默认仍用样式表。阶段 1 减少改挂之后，样式表的成本可能已不重要，先测量再决定，见 [实现计划 2.10](implementation/phase-2-themes.md#210-样式实现迁移可选先测量)。深色主题不依赖这一步，直接在现有令牌上实现。

## 5. GPU 渲染与终端视图契约

终端尚未接入，但窗口系统现在的 parent 处理方式会直接影响 GPU 方案，需要先定契约。

- **渲染路径**：终端视图使用 `QRhiWidget`（Qt 6.7 起提供），Windows 上默认走 D3D11/D3D12，失败时退到 OpenGL；部署目录已有 Mesa llvmpipe 作为软件兜底。不使用 `QPainter` 逐字绘制。
- **组合代价**：一个顶层窗口中出现第一个 `QRhiWidget` 后，整个窗口的 backing store 改为 GPU 合成；同一顶层窗口里的所有 RHI 控件必须使用相同图形 API。这要求主题和其他自绘控件在 GPU 合成下表现正常，接入时需要单独验收。
- **字形图集**：每个顶层窗口对应一个 `QRhi`，纹理不能跨 `QRhi` 共享。字形图集按“窗口 × 字体 × DPR”共享给该窗口内的所有终端，而不是每个终端一份；图集有字节上限，按最近使用淘汰。
- **帧节奏**：终端输出只标记脏行，通过 `QWindow::requestUpdate()` 按显示刷新率合并；一帧内多次输出只绘制一次。不可见的终端不生成渲染数据。
- **吞吐**：vtebench 一类测试主要比拼 VT 解析和“不为每个字节绘制”。解析放在每会话的读取路径中（不占 GUI 线程），GUI 线程只取渲染快照。窗口系统的责任是：标签切换和布局变化不触发终端视图重建、不改 parent（第 1、2 节）。
- **接入契约**（建议写入 `window-system-design.md`）：内容控件可以是原生或 RHI 控件；模块保证同一顶层窗口内移动不改 parent，跨顶层窗口移动只改一次 parent，并在之前通过可见性回调通知宿主释放 GPU 资源。

## 6. 测量与预算

现有夹具测的是对象和句柄是否回落，没有规模测试。建议新增 `tools/bench/`，或 `modules/window-system/tests/bench/` 下不进默认 CTest 的基准程序，固定输出 JSON 到 `out/test-results/`：

| 场景 | 记录 |
| --- | --- |
| 创建 100／500／1000／2000 个占位标签 | 总耗时；每个标签的私有提交增量；QObject／QWidget 数 |
| 上述规模下关闭一个标签、移动一个标签、拆分一个窗格 | 单次 `refresh()` 耗时 p50／p95 |
| 拖动分隔条 100 次 | 每次移动的处理耗时 |
| 1000 个标签时连续按键 1000 次（无匹配绑定） | 每次按键在事件过滤器中的耗时 |
| 1000 个标签的布局保存 | JSON 字节数、写盘耗时 |
| 循环开关 1000 次 | 私有提交、句柄、GDI／USER 计数趋势 |

先跑出基线，再按 [工程设计 §4](../development/engineering-design.md) 的 p95 ≤ 50 ms 原型目标定各项预算并写入测试。没有测量结果之前，不在文档或提交说明里写“已达到”。

## 7. 其他

- **布局保存**：标签上千时，可改用紧凑 JSON（`QJsonDocument::Compact`）并放到工作线程写盘（GUI 线程只生成快照），先测量第 6 节的保存项再决定。
- **命令目录**：命令数增长到几千时，`CommandRegistry::find()` 改为 ID→下标哈希。本轮的按键候选索引已经去掉了最频繁的全量复制。
- **应用级事件过滤器**：`qApp->installEventFilter` 会看到 GUI 线程的所有事件。现在入口判断很轻，以后加逻辑时要保持“先按事件类型快速返回”。
