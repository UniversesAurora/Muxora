# 未来规划

记录已经确定“以后要做”、但现在不设计实现方式的事项。这里只写需求和必须遵守的约束；真正开始做时，再写设计文档和实现步骤，并把条目移到对应的设计里。

## 1. Windows 7 Aero 风格的外观

**需求**：在现有的 Visual Studio 2019 之后的风格之外，提供一套 Windows 7 Aero 风格的外观，作为可以切换的主题版本。

**已知约束**：

- 这不只是换颜色：Aero 有半透明玻璃、渐变、高光、圆角等，需要的不只是主题颜色 ID，还可能需要单独的绘制样式（[主题系统设计](../design/theme-system-design.md) 目前只覆盖颜色）。开始设计时要评估：哪些靠颜色与样式参数实现，哪些需要专门的绘制代码，以及 Windows 10／11 上半透明效果的系统接口和性能。
- 与现有主题共用颜色注册表、组件画廊和三套截图评审流程（[界面设计规范 §6](../design/ui-design-system.md#6-评审与验收)）。
- 不影响默认的 Visual Studio 风格，也不增加不使用这套外观时的内存占用（按需加载，[工程设计 §3.4](../development/engineering-design.md#34-不用的组件不加载)）。

## 2. AI 接入

**需求**：以后接入 AI 能力。AI 发展很快，现在不确定具体形式，也暂时不需要，先记录方向和约束。

**可能的用途**（不是承诺，开始设计时再取舍）：

- 解释终端输出或报错，给出可能的原因；
- 用自然语言描述要做的事，生成命令，由用户确认后再执行；
- 帮助编写 Lua 脚本、`settings.json` 和快捷键配置；
- 总结一段会话日志或一次操作的过程。

**必须遵守的约束**：

- **默认关闭**，用户明确开启后才可用；没开启时不加载任何相关组件，不占内存（工程设计 §3.4）。
- **不自动发送数据**：任何终端内容、文件、配置要发给 AI 服务之前，都由用户主动发起，并能看到要发送的内容；不在后台持续上传。
- **不自动执行**：AI 生成的命令和修改只作为建议显示，执行或写入必须由用户确认。
- **用户选择服务**：服务提供方（在线服务或本地模型）、地址和密钥由用户配置；密钥存入系统凭据库。
- **复用已有机制**：通过命令、快捷键、内置编辑器、Lua 扩展 API 接入，不另起一套界面体系；外观遵守界面设计规范。
