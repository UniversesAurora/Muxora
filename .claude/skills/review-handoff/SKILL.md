# 审查其他助手交回的工作

Claude 负责规划、审查和派活，其他助手按交接记录执行步骤（[AGENTS.md · 轮流开发与交接](../../../AGENTS.md#轮流开发与交接)）。执行步骤的助手能力不一，不能假定它懂项目惯例，所以逐项核对，不凭交接记录的说法下结论。发现的问题直接修，修不了或要改架构、改用户能看到的行为时再问用户。

## 1. 弄清范围

1. 读 [交接记录](../../../docs/development/handoff.md) 最上面几节，找到 Claude 上一次交出时的提交，记为基线。
2. `git status --ignored -s`、`git log --stat <基线>..HEAD`、`git diff --stat <基线>..HEAD`。逐个提交看，不只看最终差异：中间提交可能带进又删掉了东西，提交说明本身也会公开。
3. 读这几步在实现计划里的原文（目标、实现、测试、验证、完成标准），审查以原文为准。用 `git diff <基线>..HEAD -- docs/roadmap` 看执行者有没有改写计划原文来迁就实现。

## 2. 先复核验证

构建一次，跑交接记录提到的套件；桌面和全量测试按 AGENTS.md 经 `quiet-desktop.ps1 -Elevate`。数字和记录不符时先记下来。不重跑执行者已跑过的全量，除非接下来要改代码（改完本来就要跑）。

## 3. 代码

- **达成目标**：对照计划逐条核对。缩小了范围、换了做法或跳过的部分，计划“状态”里必须写明原因；写成“用法”的限制要退回用户决定。
- **改动的每个分支**：重构或合并分支时最容易丢一行。逐个函数对比改前改后，例如原来两处都设置的标记，新代码只在一个分支里设了。
- **设计**：复制粘贴的函数合并成一个；模块边界（`modules/window-system` 不依赖 Muxora）；计划之外新增的公开 API；死代码、重复查找、过度防御的检查；注释和周围代码的密度、语气一致。
- **性能**：刷新、焦点变化、绘制、逐标签循环这类热路径上新增的遍历、分配、系统调用；阶段约束要求的基准有没有跑、数字从哪来。
- **命名**：符合周围代码的习惯，英文标识符，不出现厂商名、本机软件名。
- **测试**：断言被删或放宽、超时或阈值调大、为通过而改预期（[测试要求 §1](../../../docs/development/testing-design.md#1-必须遵守的规则)）；新测试在旧代码上是否真的会失败；测试依赖本机装的特定软件。
- **界面**：复用现有控件以外的新组件或新外观，执行者应该停下来交给 Claude。

## 4. 文件和仓库

- 多出来的文件：临时脚本、备份、诊断输出、空目录、提交进来的 `out/` 内容。
- 删除和改名：`git diff --diff-filter=DR --stat <基线>..HEAD`，每个删除都要有理由，误删的恢复。
- 大面积无关改动：整份重排、换行符或缩进变化、生成文件被手改（翻译目录只能由 lupdate 目标生成）。
- 提交粒度和格式按 [参与开发](../../../CONTRIBUTING.md#提交改动)：一个提交一件事。

## 5. 文档

- 按 [文档维护规范](../../../docs/development/documentation.md)：每类信息只在权威位置写一次，别处链接；模块 README 和设计文档不要互相复述。
- 计划的“实现与计划的差别”只写真正的差别；数字和结论写在验证日志，计划和交接记录给链接。
- 验证日志：每个数字对应一次运行、一个代码版本；未执行、跳过的如实写。
- 经验文档按 [怎么写一条经验](../../../docs/development/lessons/README.md#怎么写一条经验) 的字段，同一个问题只写一条，有“出处”。
- 公开仓库不写本机信息：已装软件名、输入法名、布局数量、CLSID/GUID、路径、用户名。也要查提交说明。已推送的历史有这类内容时告诉用户，改写历史要用户明确同意。
- 对外文字按 `shuorenhua` skill；运行 `python tools/check-docs.py`。

## 6. 修正和记录

- 直接修，一类问题一个提交（例如“代码缺陷 + 回归测试”“文档整理”分开），提交说明写清楚是审查发现的。
- 验证日志加一节“审查 <助手> 的 <步骤> 提交”：基线、发现的问题、修正和验证。
- 能归纳成一句做法的问题，都写进 [助手协作经验](../../../docs/development/lessons/collaboration.md)（执行者接手时会先读它），同时把查出它的方法补进本清单对应的一节。已有同类经验的，在那条下面补“复发”，不另写一条。
- 在对话里告诉用户：审查了哪些提交、发现什么、修了什么、还有什么要用户决定。

## 7. 派下一步

用户说要交接时，交接记录最上面一节写给下一位执行者（工作中不用每步更新）：做哪一步、涉及哪些文件、做到什么程度算完、要跑哪些验证、遇到新界面设计时停下。执行者接手后不审查 Claude 的提交，所以要交代的事都写在这里。
